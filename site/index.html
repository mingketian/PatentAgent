The problem

Prior-art search fails in three specific ways.

Each failure needs a different fix, which is why the system is built as separate, named stages rather than one prompt.

Failure 01

Vocabulary mismatch

Patent claims describe the same invention in deliberately different language. A plain-language query misses art whose wording differs but whose technical content overlaps almost entirely.

→ Dense retrieval + a learned reranker over dense, BM25 and field-lexical signals.
Failure 02

Ranking is not analysis

A ranked list does not say why a patent is relevant, or which limitation of your claim it reads on. The reader still has to do all the work.

→ Limitation-level evidence extraction — each limitation mapped to a specific snippet.
Failure 03

Fluent but unsupported

A one-shot LLM answer sounds authoritative while inventing patent mappings. In a legal workflow, an unsupported claim-to-evidence mapping is worse than no answer.

→ A separate verification pass labels the answer supported / partial / unsupported.
Architecture

One index, two paths.

The baseline retrieves and stops. The agent adds learned reranking, evidence alignment, grounded synthesis and verification on top of the same shared patent store — which makes the comparison between them exact.

01 · PLAN

Planner & decomposition

Classifies the turn — new search, follow-up, comparison, aspect filter, combination — and splits the claim into limitations.

src/query_planner.py
02 · RECALL

Coarse recall

A single FAISS query returns 4·k candidates from 768-d PatentSBERTa vectors. Deliberately wide — the reranker cannot recover what recall missed.

src/persistent_index.py
03 · RERANK

Linear patent reranker

Logistic regression over dense, bm25 and field_lexical — the last weights title, abstract and claims separately.

src/train_linear_patent_reranker.py
04 · ALIGN

Evidence extraction

Scores every title, abstract and claim segment against every limitation, and keeps the best match as the claim chart.

src/claim_analysis.py
05 · SYNTHESISE

Grounded answer

Answers from the extracted evidence. Heuristic by default — the system is grounded without an API key; the LLM only adds fluency.

src/free_text_qa.py
06 · VERIFY

Answer verification

Re-reads the answer against the evidence and labels it supported, partially supported, or unsupported — with the overlap score as the reason.

src/claim_analysis.py
Follow-ups reuse the working set. When the planner reads a turn as a filter or a comparison over previous results, the agent reranks the existing candidates instead of starting a new search. That single decision is where the 0.98 context-reuse score comes from.
Results

Measured twice: ranking, then answers.

Retrieval metrics on a labelled benchmark say whether the ranking improved. They say nothing about whether the answer a user reads is trustworthy, so we measured that separately by hand.

The learned reranker is best on all four metrics. The largest gain is on Exact@|gold| — +5.2 points over the PatentSBERTa baseline — which is the metric that asks whether the system recovers the exact gold prior-art set, not just one member of it.
The interesting result is the trade-off the agent escapes. Plain RAG is safe but useless — 0.95 hallucination-free, 0.20 helpful, with zero top helpfulness labels across all 20 prompts, because a ranked list is not an answer. The general assistants are the mirror image: fluent and reasonably helpful, but grounded on 1 and 0 of 20 answers respectively. Our agent is the only system that is helpful and grounded at the same time.

Read honestly: RAG only beats us on hallucination-freedom, 0.95 to 0.90. Generating an answer at all costs something. The claim is not that the agent is the safest possible system — it is that it buys a 4.25× improvement in helpfulness for a 0.05 drop in hallucination-freedom. Full protocol, rubric and limitations are in docs/HUMAN_EVALUATION.md.

Run it

Clone, activate, launch.

The repository ships a 112-patent demo index and the trained reranker weights, so both interfaces start immediately with no build step and no API key.

1 Environment

Python 3.10 via conda. The benchmark mode also wants PANORAMA as a sibling directory.

# clone and set up
git clone https://github.com/mingketian/PatentAgent.git
cd PatentAgent
conda env create -f environment.yml
conda activate patent-agent

# benchmark mode only
git clone https://github.com/LGAI-Research/PANORAMA.git ../PANORAMA

2 Launch

Two interfaces over the same components — a FastAPI single-page demo, and a Streamlit app with side-by-side baseline comparison.

# web demo → http://localhost:8899
make web

# streamlit app → http://localhost:8501
make app

# CLI
python -m src.run_free_text_demo

3 Reproduce the benchmark

The full validation run over all three methods — the numbers on this page.

python -m src.evaluate_par4pc_hf \
  --splits validation \
  --max-rows-per-split 3029 \
  --methods bm25 local-embedding \
            linear-patent-reranker

4 Retrain the reranker

Three features, 200 cases, seconds. Weights are written to data/models/.

make train

# or regenerate all figures + tables
make figures

Limitations we will state plainly

  • Answer quality is bounded by index coverage. The agent can only ground an answer in patents that are in the index.
  • Benchmark scope is PAR4PC. An 8-candidate reranking task is easier than open-corpus retrieval over the full patent universe.
  • The human study is small and internally annotated. 20 prompts × 4 systems = 80 answers, labelled by the project team, not by independent patent professionals.
  • Retrieval metrics exclude the generation stack. They measure ranking only — not decomposition, query expansion, answer generation or verification.
  • Not legal advice. This is first-pass prior-art triage.
